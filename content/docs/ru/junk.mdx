На домен подписки постоянно стучатся сканеры: перебирают `/.env`, `/wp-login.php`, `/xmlrpc.php` и тысячи других адресов в надежде найти чужой сайт. Прослойка отвечает им 404, но каждый такой запрос всё равно проходит через PHP и добавляет записи в лог. Самые частые адреса проще отсекать на веб-сервере — до прослойки, без PHP и без записи в лог.

Порядок простой: **сутки смотрим, что ходит часто → выбираем адреса, которые точно не ваши → добавляем правила в веб-сервер → проверяем, что подписка и страница подписки работают**.

## Что показывает «Мусор» [#junk-stats]

Вкладка «Лог запросов → Мусор» собирает все запросы, которые не похожи на подписку: последние 500 целиком (время, IP, путь, клиент, ответ) и сводки по адресам и по IP. Правила на этой же вкладке умеют отвечать сканеру сразу, не ходя в панель (копия настоящего 404, пустой 404 или 403), по пути, IP или части User-Agent. Это удобно для точечных решений и для блокировки IP на время, но каждый запрос всё равно обрабатывает PHP.

<Callout type="info">
Прослойка по умолчанию ничего не режет — что отсекать, решаете вы. Готовые наборы на вкладке «Мусор» выключены.
</Callout>

## Шаг 1. Посмотрите сутки [#junk-watch]

Откройте «Мусор» через сутки после установки (или через сутки после последней чистки сводки) и отсортируйте сводку по адресам по числу запросов. Обычно картина такая:

| Адрес | За сутки | Что это |
|---|---|---|
| `/.env` | 140 | поиск файлов с паролями |
| `/wp-login.php`, `/wp-admin/`, `/xmlrpc.php` | 120 | перебор WordPress |
| `/.git/config` | 60 | поиск открытых репозиториев |
| `/phpmyadmin/`, `/pma/`, `/mysql/` | 45 | поиск phpMyAdmin |
| `/vendor/phpunit/…/eval-stdin.php` | 30 | известная уязвимость PHPUnit |
| `/cgi-bin/`, `/boaform/`, `/GponForm/` | 25 | уязвимости роутеров |
| `/admin/` | 20 | подбор админок — **наш собственный адрес, его не трогаем** |

Отсекать стоит только то, что стабильно повторяется и заведомо не имеет отношения ни к подписке, ни к прослойке. Один-два запроса на адрес в сутки не стоят правила.

## Шаг 2. Чего резать нельзя [#junk-keep]

У прослойки есть собственные адреса, и часть из них снаружи выглядит как мусор. Правило на веб-сервере с таким адресом сломает работу — и вы об этом узнаете не сразу, потому что до прослойки запрос уже не дойдёт и в логе его не будет.

| Адрес | Зачем нужен |
|---|---|
| `/<префикс>/<метка>` и `/api/sub/<метка>` | сама подписка; метка — случайная строка, по виду неотличима от мусора |
| `/<префикс>/c1/…` | защищённый канал Clod Clash: три случайных сегмента после `c1/` |
| `/a1/…` | канал приложения для Android |
| `/webhook.php`, `/chat.php` | вебхуки панели и чат поддержки |
| `/admin/` и всё под ним | админка, в том числе вход по секретной ссылке |
| `/<32 буквы и цифры>` | планировщик «по адресу», если он у вас включён |
| `/assets/`, `/.well-known/`, `/cdn-cgi/`, `/assets/.app-config-v2.json`, `favicon.ico`, `robots.txt` | страница подписки в браузере и проверки сертификатов |
| `/` | страница-приманка на корне домена |

Отсюда три правила:

* **Не превращайте все 404 в обрыв.** Запрос с несуществующей меткой подписки тоже получает 404 от панели — это нормальная работа, а не мусор. Правило «всё, что не нашлось, — 444» отсечёт и такие запросы, и удалённых пользователей, и опечатки в ссылках, и вы перестанете видеть их в логе.
* **Не режьте по короткому префиксу.** `location /a` или `path /c*` зацепит и подписку, и каналы. Только полные пути или узкие шаблоны вроде `/wp-*`, `/\.env`, `/\.git/`.
* **Не трогайте скрытые файлы целиком.** Правило `/\.` закрыло бы `/.well-known/`, через который выпускаются сертификаты. В примерах ниже оно исключено явно.

Если префикс подписки или защищённый канал вы не включали, соответствующих адресов у вас нет — но ограничения всё равно безопаснее оставить: включить их можно позже и забыть про правило на веб-сервере.

## Шаг 3. Добавьте правила на веб-сервер [#junk-web]

Ответ `444` у nginx означает «закрыть соединение, ничего не отвечая» — для сканера это выглядит так, будто на адресе никого нет. У Caddy то же делает `abort`. Прослойка при этом не задействована вовсе.

<Tabs groupId="web" persist items={['nginx', 'Caddy']}>
<Tab value="nginx">

Добавьте блок в `server` сайта **перед** `location ~ \.php$` — иначе `wp-login.php` уйдёт в PHP раньше, чем сработает правило. Файл — тот же, где лежат правила из установки: конфиг сайта на хостинге или `nginx.conf.template` рядом с `docker-compose.yml`.

```nginx title="nginx"
# Сканеры: закрыть соединение без ответа. Только адреса, которых у прослойки нет.
location ~* ^/(wp-admin|wp-content|wp-includes|wordpress|phpmyadmin|pma|mysql|cgi-bin|boaform|GponForm|vendor/phpunit)(/|$) { return 444; }
location ~* ^/(wp-login\.php|xmlrpc\.php|\.env(\.[a-z]+)?|\.git(/.*)?|\.svn(/.*)?|\.DS_Store|composer\.(json|lock)|package\.json)$ { return 444; }
```

Если в конфиге из установки есть строка `location ~ /\.(?!well-known) { deny all; }` и она стоит выше, скрытые файлы (`.env`, `.git`) получат от неё 403 раньше, чем дойдут до правила 444, — так и задумано, оставьте. Хотите и для них обрыв — замените в этой строке `deny all;` на `return 444;`. Исключение для `.well-known` в ней обязательно.

Проверьте конфиг и перечитайте его: `nginx -t && nginx -s reload` (в Docker — `docker compose exec nginx nginx -t`, затем `docker compose restart nginx`).

</Tab>
<Tab value="Caddy">

Добавьте в блок сайта в `Caddyfile` — порядок внутри блока не важен, Caddy выполняет `abort` раньше `php_fastcgi`. Файл — тот же, что при установке: `Caddyfile` сайта или рядом с `docker-compose.yml`.

```text title="Caddyfile"
	# Сканеры: закрыть соединение без ответа. Только адреса, которых у прослойки нет.
	@junk {
		path /wp-admin/* /wp-content/* /wp-includes/* /wordpress/* /phpmyadmin/* /pma/* /mysql/* /cgi-bin/* /boaform/* /GponForm/* /vendor/phpunit/*
		path /wp-login.php /xmlrpc.php /.env /.env.* /.git /.git/* /.svn /.svn/* /.DS_Store /composer.json /composer.lock /package.json
	}
	abort @junk
```

Проверьте и перечитайте: `caddy validate --config /etc/caddy/Caddyfile && caddy reload --config /etc/caddy/Caddyfile` (в Docker — `docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile`).

</Tab>
</Tabs>

<Callout type="warn">
Прослойка стоит рядом с панелью за её реверс-прокси? Тогда правила добавляются в блок домена подписки у того прокси, который принимает запросы первым — обычно это Caddy или nginx самой панели. Внутри контейнера прослойки править нечего.
</Callout>

Если перед сервером стоит Cloudflare или другой внешний прокси, клиент увидит не обрыв, а его ошибку (например, 520) — это нормально, цель та же: запрос не доходит до прослойки.

## Шаг 4. Проверьте [#junk-check]

```bash
curl -i https://sub.example.com/wp-login.php                      # curl: (52) Empty reply from server — обрыв
curl -I https://sub.example.com/.well-known/acme-challenge/test   # 404, но не обрыв: путь не закрыт
curl -I "https://sub.example.com/<ваша ссылка подписки>"          # 200 и заголовки подписки
```

Откройте ссылку подписки в браузере — страница должна загрузиться со стилями, — и в клиенте. Если включён защищённый канал или приложение для Android, проверьте и их. Через сутки загляните в «Мусор»: отсечённых адресов в сводке больше не будет, остальные правила админки продолжают работать как раньше.

Раз в месяц повторяйте шаг 1: сканеры меняют списки, а в статистике будет видно, что появилось нового.
